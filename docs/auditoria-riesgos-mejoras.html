P0 - Riesgo critico

Bearer invalido termina en error 500

P0 Seguridad

Que es El middleware deja pasar peticiones con cabecera Bearer, pero si el token no es valido algunos handlers acaban lanzando una excepcion desde la resolucion de usuario.

Implicaciones La API puede devolver 500 en vez de 401. Esto empeora la UX de clientes externos, ensucia logs, dificulta depuracion y puede ocultar fallos reales de permisos.

Parte humana Confirmar contrato de errores: 401 para no autenticado, 403 para autenticado sin permiso y 404 cuando convenga no revelar recursos.

Parte por codigo Crear helper/wrapper de auth para handlers, devolver JSON consistente y añadir tests de tokens invalidos.

Secreto de pagos reutiliza AUTH_SECRET

P0 Seguridad

Que es La configuracion de webhooks o pagos puede caer en FOOD_PAYMENT_WEBHOOK_SECRET || AUTH_SECRET, compartiendo un secreto de autenticacion general con una integracion de pagos.

Implicaciones Aumenta el radio de impacto si se filtra un secreto y complica rotaciones: cambiar pagos podria afectar sesiones o autenticacion principal.

Parte humana Generar un secreto dedicado, cargarlo en entornos reales y decidir si hace falta rotar secretos existentes.

Parte por codigo Hacer obligatorio FOOD_PAYMENT_WEBHOOK_SECRET, eliminar fallback, actualizar .env.example y cubrirlo con tests.

No hay CI de PR para typecheck, tests y build

P0 DX / Operacion

Que es El repositorio no tiene una validacion automatica completa en pull requests o pushes principales.

Implicaciones Cambios con errores de tipos, tests rotos o fallos de build pueden llegar a main y bloquear despliegues posteriores.

Parte humana Activar secrets necesarios y, si se desea, reglas de proteccion de rama en GitHub.

Parte por codigo Crear workflow de GitHub Actions con install, Prisma generate, typecheck, tests, lint y build segun scripts disponibles.

P1 - Prioridad alta

ownerId nullable en entidades multi-tenant

P1 Arquitectura

Que es Algunas entidades permiten ownerId nulo aunque el sistema se basa en aislar datos por propietario.

Implicaciones Aumenta el riesgo de datos huerfanos, consultas dificiles de auditar y errores de aislamiento entre usuarios si una ruta olvida filtrar correctamente.

Parte humana Decidir que usuario reclama datos huerfanos y si se permiten flujos anonimos temporales.

Parte por codigo Preparar migracion, script de reclamacion, restricciones Prisma y tests de aislamiento por ownerId.

Rate limiting OTP solo por email

P1 Seguridad

Que es El control de intentos de OTP se centra en el correo, pero no limita suficientemente por IP, dispositivo o ventana global.

Implicaciones Puede permitir bombardeo de emails o fuerza bruta distribuida, generando coste, ruido y friccion de seguridad.

Parte humana Definir politica de limites, duracion de bloqueos y tolerancia para usuarios legitimos.

Parte por codigo Añadir contador por IP/email con hash, ventanas temporales, respuestas 429 y tests de abuso.

Faltan tests de rutas criticas

P1 Calidad

Que es Hay cobertura insuficiente para handlers de auth, pagos, comida, permisos y scraping.

Implicaciones Cambios pequeños pueden romper flujos de login, pedidos, importacion o permisos sin detectarse hasta uso real.

Parte humana Aprobar alcance de cobertura y si los tests usan mocks o base de datos de test.

Parte por codigo Crear tests de integracion enfocados, fixtures y comprobaciones de respuestas HTTP esperadas.

Busqueda global con contains insensitive

P1 Rendimiento

Que es La busqueda depende de filtros tipo contains, que son simples pero escalan mal en tablas grandes.

Implicaciones A medida que crezca el catalogo, las busquedas pueden volverse lentas y consumir demasiada CPU en Postgres.

Parte humana Aceptar una migracion de indices y decidir campos relevantes para ranking de busqueda.

Parte por codigo Añadir busqueda full-text o indices GIN, adaptar consultas y medir planes antes/despues.

Recheck de anuncios secuencial y lento

P1 Rendimiento

Que es El proceso checkAllActiveListings revisa anuncios uno a uno con pausas fijas.

Implicaciones Puede tardar demasiado, chocar con timeouts y dejar estados o precios obsoletos cuando el volumen suba.

Parte humana Definir limites de concurrencia por portal y politica prudente de scraping para evitar bloqueos.

Parte por codigo Implementar concurrencia controlada, backoff, metricas e ImportLog mas util para seguimiento operacional.

P2 - Prioridad media

Desfase entre documentacion BuySell y app Nidokey

P2 Arquitectura

Que es La documentacion historica describe BuySell inmobiliario, pero el codigo ya incluye verticales como comida, chat y servicios.

Implicaciones Provoca decisiones inconsistentes, onboarding confuso y mayor riesgo de tocar piezas equivocadas.

Parte humana Confirmar nombre, alcance actual y roadmap real del producto.

Parte por codigo Actualizar README, AGENTS, roadmap y docs tecnicas para reflejar el estado actual.

Prefijo de tokens inconsistente: bs_ vs nk_

P2 Seguridad

Que es Algunos documentos o scripts hablan de tokens bs_, mientras el codigo genera o espera nk_.

Implicaciones No es una vulnerabilidad directa, pero dificulta soporte, pruebas y depuracion de bookmarklets o clientes externos.

Parte humana Elegir prefijo oficial para la marca actual y si se mantiene compatibilidad con tokens antiguos.

Parte por codigo Unificar documentacion, comentarios, validadores y mensajes de error; añadir compatibilidad temporal si se decide.

OTP y magic links pueden imprimirse en logs dev

P2 Seguridad

Que es Cuando falta Resend, el flujo de desarrollo puede mostrar codigos OTP o enlaces magicos en consola.

Implicaciones Es util en local, pero peligroso si ocurre por error en staging o produccion porque revela acceso en logs.

Parte humana Decidir si staging permite modo debug o debe fallar si falta el proveedor de email.

Parte por codigo Restringir logs sensibles a NODE_ENV=development y fallar rapido en produccion si falta configuracion.

Listado de pedidos carga eventos completos

P2 Rendimiento

Que es La lista puede incluir eventos completos de muchos pedidos en vez de traer solo resumenes.

Implicaciones El endpoint crece en peso y latencia, especialmente en mobile o dashboards con muchos pedidos.

Parte humana Decidir que datos necesita realmente la lista frente al detalle de pedido.

Parte por codigo Crear DTO de resumen, endpoint de detalle y pruebas para tamaño y forma de respuesta.

Scraping de menus borra y recrea items

P2 Rendimiento

Que es La actualizacion de menus puede sustituir el menu completo en vez de aplicar diferencias sobre platos existentes.

Implicaciones Genera churn en base de datos, IDs inestables y mas riesgo para carritos, favoritos o referencias futuras a platos.

Parte humana Definir regla de identidad de plato: nombre normalizado, categoria, variante, precio o combinacion.

Parte por codigo Implementar upsert/diff estable, mantener IDs cuando sea posible y cubrir cambios con tests.

P3 - Mejora y deuda tecnica

IP LAN hardcodeada en la app mobile

P3 DX

Que es El cliente mobile puede depender de una IP local concreta en vez de configurarse siempre por variable de entorno.

Implicaciones En otro equipo o red deja de funcionar sin tocar codigo, y es facil commitear valores locales por accidente.

Parte humana Definir URL local recomendada para desarrollo fisico, simulador y entorno publicado.

Parte por codigo Usar EXPO_PUBLIC_API_URL como fuente unica, actualizar ejemplos y mensajes de setup.

No hay script npm test estandar

P3 DX

Que es Existen tests, pero falta un comando convencional npm test para que personas, agentes y CI los ejecuten igual.

Implicaciones Aumenta la friccion y hace mas probable que se omitan pruebas antes de subir cambios.

Parte humana Aprobar convencion de runner y si se separan tests unitarios, integracion y smoke.

Parte por codigo Añadir scripts npm coherentes y conectarlos con CI.

menu-scrape.ts concentra demasiadas responsabilidades

P3 Calidad

Que es El modulo de scraping de menus mezcla resolucion de fuentes, extraccion, normalizacion y persistencia.

Implicaciones Los cambios son mas dificiles de razonar y testear, y se vuelve mas facil romper Google, Firecrawl o persistencia al tocar otra parte.

Parte humana No requiere decision funcional, solo elegir el momento para el refactor.

Parte por codigo Separar resolver, extractor, normalizador y persistencia, manteniendo comportamiento y tests de regresion.

orderCode usa Math.random

P3 Seguridad

Que es El codigo corto de pedido se genera con una fuente pseudoaleatoria no criptografica.

Implicaciones El riesgo es bajo si solo se usa para soporte, pero conviene evitar codigos predecibles en identificadores visibles.

Parte humana No requiere decision humana salvo cambiar formato visible del codigo.

Parte por codigo Sustituir por crypto.randomInt o randomBytes y añadir tests de formato.
